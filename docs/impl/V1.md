## Findings
- Where the 2D stretch really was: menus scale by s = W/640 (SPEC-800), so at 16:9 the 4:3 pages are 33 % too
  big vertically (the bottom of `video`, the control bar, is cut — capture `menus1080s0\video.png`); the HUD pics
  and the SoF fonts are drawn 1:1 (not stretched) in OpenMerc as in the original, only the scope/rank/flag x
  offsets used W/640; the Yamagi console used an integer scale (3 at 1080p, 24 px glyphs).
- `r_mode -2` was already handled (`SetMode_impl` → `GLimp_GetDesktopMode`); borderless = `vid_fullscreen 2`
  works on SDL3 (`Setting mode -2: 2560x1440 (vid_fullscreen 2)`).
- The GL3 renderer had `r_msaa_samples` (applied at context creation → Apply's `vid_restart`) and a registered
  but unused `r_anisotropic`; SoF's `gl_ext_anisotropic` gave a fixed 2x. Wired as in the table above.
- Colour table: `GL3_SoF_BuildColorTable(gamma, brightness, contrast)` uses all three (SPEC-413 §9), rebuilt at
  renderer start (Apply's `vid_restart`); `gl_modulate` is latched at start too → all four sliders kept.
  `vid_gamma` prints `0.0` on a fresh start (SoF neutral), so the colour table is right by default.
- Rows dropped (nothing behind them in GL3): video driver, bit depth, alternate textures (`gl_pictip`), texture
  quality (`gl_picmip`/`ghl_mip` — the renderer has the cvars but the page is about display; they stay at the
  defaults), texture formats / S3TC. Kept dynamic rows: `ghl_light_method`, `ghl_specular` (used by
  `gl3_ghoul.c`), `gl_detailtexturing` + distance (`gl3_detail.c`), `gl_texturemode`.
- `vid_maxfps`: Yamagi targets refresh × 1.2 under vsync when `vid_maxfps` ≥ refresh − 2 and lets vsync
  throttle; with `0` = refresh the behaviour is the same (vsync on) and exactly the refresh rate with vsync off.
- The deferred `vid_restart` (Yamagi) made the Apply key list build the new pages for the old window: the first
  Apply capture was a 1080p layout cropped to 1280x720. Fixed by `M_RebuildScreens` (also covers a `scr_aspect`
  change while menus are open).
- Mixed language: this install's zmain overwrote the English slot of the stock packages with Russian, so the
  reused references (`^MENU_VIDEO_RESOLUTION^`, `^MENU_SCALE_OFFON^` …) show Russian and the new rows English
  (capture `menus1080\video.png`). A Russian `menu_omvideo` would need a translator; not done.
- Harness: the original `defsnd.dll` blocks on the hidden desktop (`s_nosound 1` is not honoured by it; the first
  plain run hung at "Loading defsnd.dll" until the timeout) — every run uses `snd_dll OMsnd.dll` with
  `s_om_wavefile`. The first plain run with OMsnd and no wave file opened the real audio device
  ("OpenAL Soft on Динамики"): 30 s of intro audio may have reached the speakers once; wave file since.
- `om_after` counts drawn frames; the disclaimer → intro → main sequence took 5400 frames ≈ 33 s here.
- Pre-existing, not V1: console spam `GL_FindImage: Can't load pics/misc/conback` and the garbled version string
  at the bottom right of the console (Yamagi's alt-colour chars with the SoF conchars); `cl_hud.c` C4090 at
  `COM_Parse((char **)&s)`.

## HUD scaling (coordinator follow-up, 2026-10-25, commit "V1: HUD scaling")
Owner's decision: a 1:1 HUD at 1440p is not acceptable. `scr_hudscale` (archive): 0 = auto (default) = the canvas
scale s = H/480 (1 with `scr_aspect 0`), 1 = 1:1 as the original, any other value = that factor; video page row
"HUD Size : Auto / 1x / 2x / 3x" (`menu_hudscale`, staged like the rest).

Mechanism: the HUD code (`cl_hud.c`) and the SoF screen prints (`cl_sofscreen.c`) lay out in a virtual window of
`HUD_W() x HUD_H()` = W/f x H/f pixels; between `HUD_BeginScaled()`/`HUD_EndScaled()` the renderer multiplies every
2D primitive by f (`RectXY` and `Line` in `gl3_sof2d.c`, so pics, pic parts, glyphs, proportional fonts, fills and
lines all scale). The SoF ABI table `sofrefexport_t` is fixed-size (220 bytes), so the factor goes through a second
DLL export `OM_Set2DScale` (`OM_SOFREF_SETSCALE_NAME`, fetched in `HUD_Ref()`). Scaled: interface elements (positions
recomputed per frame from the virtual window, corners stay corners), scope, rank, flags, scoreboard layout,
crosshair (centred in the virtual window), remote-view bars, centre/caption/typewriter prints, credit pics, pause
text, net icon. Not scaled (window pixels): world labels (`DrawWorldLabel`, projected positions) and the debug
graphs; the Yamagi console/notify keep their own 8 s rule. Test helper `om_centerprint <text>`.

## Open questions
- HUD element size: done as `scr_hudscale` (section "HUD scaling"); the SoF fonts are nearest-filtered, so at
  non-integer factors (2.25 at 1080p) glyph edges are slightly uneven - integer factors (3 at 1440p) are crisp.
- Scope, rank, CTF/control flag anchoring (`SX`/`XL`/`XR`) is arithmetic only — kos1 single-player shows none
  of them, so no capture; the stock HUD has no vehicle/helicopter element (SPEC-310: remote view types 2/4/16
  only), the remote-view bars scale by H/480 as before.
- In-game console capture: `toggleconsole` from an exec'd script shows no console in the frame captures even with
  1000 `wait`s before `omshot` (`ingame\con1080\console2.png`, `ingame\hud1440\console.png`); the menu-level
  console capture works (`menus1080\console.png`). Harness limitation (the console scale itself is proven by the
  notify lines and the menu-level captures); a key-driven toggle would need the owner's desktop.
- Death/end screens: `kill` → `death.png`/`death2.png` are black at +2000/+4000 waits; whether that is the fade
  or a missing end screen needs the original for comparison (not a V1 regression: nothing of V1 draws there).
- Level-change loading screen: only the `menu loading` page was captured (`menus1080\loading.png`), not a live
  level change.
- Menu fonts stay at their native pixel size (SPEC-800: text is never scaled); at 1440p the page text is
  small. Scaling fonts would change every layout — owner's call.
- A live `scr_aspect` change rebuilds open menus, but the HUD/console pick it up only per frame (fine) and
  cinematics keep `cin_force43` (Yamagi's own 4:3 switch) rather than following `scr_aspect`.
- `vid_fullscreen 2` + `r_mode -2` on a multi-monitor PC: SDL picks the primary display; not tested here.
